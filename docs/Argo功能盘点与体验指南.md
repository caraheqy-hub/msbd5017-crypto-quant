功能分类和完成状态以[项目功能清单](项目功能清单.md)为统一入口；本文提供较详细的官方功能说明与体验路线。

## 先看结论

Argo 本身已经是一个包含行情、策略插件、回测、结果分析和实时交易接口的工具。我们不是从零开发这些基础功能。

我们的工作主要是：用三个固定案例发现并修正具体计算问题，写一个独立参考程序检查交易与账户计算，补充针对这三个案例的统一分析和交付核验流程。CLI 是我们的使用入口，不足以证明官方没有对应的图形界面功能。

官方 macOS 应用已经有成交、订单、标记、日志、附近行情、回测统计和历史结果入口。官方框架也已经有指标测试、端到端测试和 CI。旧说明若让人误以为这些都是我们首次提供，应以本说明为准。

## 3. 用户写公式，平台负责什么

| 决定 | 谁能控制 | 例子 |
|---|---|---|
| 指标公式与信号 | 策略作者 | 自己读行情算 EMA，或调用内置指标；收盘高于均线是否买入 |
| 下单数量和下单时机 | 策略作者，在事件接口允许的范围内 | 按可用现金的 45% 下单，已有持仓不重复买入 |
| 资金、时间、数量精度和统计设置 | 回测配置 | 初始 10000、保留两位、365 日年化 |
| 订单在何时、按什么价格成交 | 回测引擎和 broker/provider 的实现 | 官方该版本市价单按当前 bar 的 (High+Low)/2，修复版可选下一 bar Open |
| 成交后的余额、手续费扣除和账户字段 | 引擎实现 | 买入不能超过现金；Equity 应符合账户定义 |

因此，并不是“用户完全不能改”。它是开源框架，可以改源码或接入其他实现。但普通策略参数不能任意覆盖撮合内部逻辑；在策略里晚发单也不自动把原来的成交模型变成下一日开盘价。平台开发者需要正确实现并清楚说明，用户需要选用符合研究假设的模型。

## 4. EMA 初始化与预热到底是什么

EMA 的递推形式是 `E[t] = alpha * P[t] + (1-alpha) * E[t-1]`，EMA20 常用 `alpha = 2/21`。

初始化是在没有前一个 EMA 时，选择第一个 E：例如第一根价格，或前 20 根价格的均值。两种方案都可以清楚定义，但起点不同，早期数值就可能不同。

预热是先提供一段历史，让指标形成可用状态；研究者还要决定预热阶段能否交易。EMA20 的“20”是平滑周期，不表示每次只取 20 个价格并直接平均。

官方本次读取版本的 RawValue 只请求 period 根；内部函数用这 period 根做 SMA 初始化，之后的递推循环没有剩余价格可处理。因此，在这个调用路径上 EMA 会退化成 SMA。这是可定位的实现问题，不只是两种合理初始化习惯之间的区别。

我们本地改为先请求 3 × period 根，不足时回退 period 根。这解决了长历史下始终退化的问题，但仍有约定：EMA20 在不足 60 根时回退 SMA20，达到 60 根后使用滚动 60 根初始化并递推。它不是持续携带全部历史状态的标准实现，也不能宣称所有 EMA 语义问题都解决。

进一步可做：区分历史不足与其他数据错误；明确禁止交易的预热阶段；选择并测试持续递推或固定窗口方案；记录对跨库结果的影响。当前回退捕获所有取数错误，也值得收窄。

## 5. 哪些是修 bug，哪些是扩展

| 工作 | 更准确的分类与边界 |
|---|---|
| EMA 长历史下仍等于 SMA | 有源码依据的缺陷；本地修正取数窗口，但保留的预热方案还需说明 |
| 余额未跟随成交同步 | 针对账户一致性的缺陷修复；要核对现金、BuyingPower 与账本 |
| 买入检查未计手续费 | 对无杠杆现金账户是缺陷；本金够但加费用不够时应拒单 |
| Equity 与多币种估值 | 按“现金 + 各币持仓市值”的账户定义修正；不能用当前币价格估全部币 |
| 数量精度 | 特定浮点边界修复，必须同时测试不超卖、不过度上取整；不是任意 epsilon 都正确 |
| next-bar open | 成交模型扩展；对我们的收盘信号修正了不因果的成交路径，不意味着同 bar 模型在任何语境都错 |
| 限价单测试隔离 | 测试修复，不是限价单交易功能创新；next-bar 开关只延迟市价单 |
| 日期 CLI | 面向固定案例的辅助工具；官方已有订单、成交、标记及附近行情查看，不能声称首次提供信号检查 |
| 统一基准、状态、仓位和费用拆分 | 针对本项目口径的研究分析；不代表官方没有基准或统计 |
| run_id、指纹与比较 | 特定格式的记录与比较辅助；官方已有历史结果、配置和版本入口 |
| 独立 Python 重放 | 对三个案例的跨实现一致性验证，不是通用 Python 策略接入 |
| 审计包与链上登记 | 研究交付版本核验方案；本次没有独立检查链上凭据，不据此更新“已上链”的状态 |

源码能证明具体行为；要提交给上游，还需把问题整理成固定版本上的最小复现与回归测试。不要因为官方已经有测试就认为没有 bug，也不要因为我们的测试通过就认为平台全部正确。

## 6. 三种验证不要混在一起

1. **独立重放：检查计算。** 先只读取行情和规则，自己算指标、信号、订单、费用和现金，再读取 Argo 账本逐笔对照。它能发现两套实现不一致，但双方也可能共同采用有局限的规则。
2. **策略分析：解释表现。** 从统一净值、基准、仓位和费用看收益风险、市场状态差异。不能由成交一致推出未来赚钱。
3. **文件或链上核验：检查交付版本。** 哈希与登记值比较，检查拿到的文件是否仍是登记的那一版。不能由哈希一致推出回测计算正确或数据真实。

## 7. 为什么共用资金时处理顺序可能影响结果

如果数量定义为“下单时可用现金的 45%”，现金随着先前成交变化，后面的订单可能用到不同的基数。简化例子（先忽略费用）：10000 元先投入 4500，剩余 5500；再按剩余现金 45% 只能投入 2475。交换资产处理顺序，会交换谁拿到更大的资金份额。

但不能把这个例子直接说成我们每个交易日都这样。当前独立重放按 BTC、ETH 顺序：先执行该币上一日订单，再生成该币本日信号；数量按生成信号时的现金和收盘价确定。提交订单并不立即扣现金，因此两个信号有时会看到相同现金，有时因中间成交而看到不同现金；真正成交时还会重新检查是否买得起。

这是需要公开的事件顺序约定。更清晰的组合引擎可以分阶段：处理所有资产开盘成交 → 更新账户 → 收齐所有收盘信号 → 统一分配预算。但改成这种模型会改变结果，必须形成新版本，不能当成无影响的整理。

## 8. 怎么体验：先认清原生功能，再看我们的扩展

### macOS 原生应用路线

当前这台电脑是 Windows，无法在本机运行原生 SwiftUI macOS 应用。以下是根据官方界面源码整理的体验路线，尚不是本次实际点击记录。完整体验需要能运行该应用的 Mac，以及数据与编译后的 WASM 策略。

1. 新建或打开 `.rxtrading` 项目，确认 data、strategy、result 三个目录和 schema。
2. 进入数据区，选择一个 Parquet，分别看表格和价格图；核对时间、币种与周期。
3. 导入官方示例 WASM，查看名称、描述与参数 schema；在项目 schema 中配置策略和引擎。
4. 选择数据与 schema，运行回测；观察运行状态、结果目录与历史结果列表。
5. 打开一份结果，进入 General 的 Info 和 Charts；查看收益、基准、费用、回撤与月度图，核对字段含义。
6. 进入 Trades，切换成交、订单和 Marks；打开一行详情与附近行情。找到策略实际写入的 Reason 和标记。
7. 查看 Logs，找一次数据不足、未执行或异常；判断这是策略没有信号、订单失败还是历史不足。
8. 查看结果附带的 Backtest Config 与 Strategy Config；换一个参数运行，检查两次历史结果是否保留。
9. 如果使用外部 agent，再体验官方 MCP 的列出数据/策略、读写 schema、运行回测和读取结果。
10. 最后查看 Live、provider 与钱包界面。本项目历史回测优先；本指南不执行真实下单，也不把文档中的连接能力视为已实测。

体验时记录“界面已能做什么、还需人工拼接什么”。例如：已有附近行情表，但能否直接联查某一日的独立指标值、预热状态、信号理由、次日成交和共享账户现金？只有实际确认后的缺口，才值得继续开发。

## 9. 对大作业定位的直接影响

可主张：我们以 Argo 为基础，用三个案例复现具体问题，在自己的版本提供修复与测试，建立独立复算、统一分析和研究交付核验流程。

不应主张：我们发明了回测、首次提供信号查看、首次保存实验结果、首次建立 CI，或已证明全面优于成熟平台。

下一步先完成原生功能体验和上游问题复现，再决定做哪个界面补充。真正有意义的验收问题是：能否更快定位一个计算差异？审核者能否从行情和规则复算交付结果？哪一步确实减少了人工核对？把这些用具体任务和证据回答，比堆功能数量更有说服力。
