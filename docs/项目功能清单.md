# 项目功能清单

盘点日期：2026-11-20；链上与交付状态同步：2026-11-28。供组员了解项目、分工、开发与准备汇报使用。**本文是功能与完成状态的统一入口。**

策略库、实验管理和 AI 相关的更详细重复功能核查见[专项核查](策略库与实验管理_Argo重复功能核查.md)。官方已有原生 run ID、配置快照、多次结果汇总、WASM 哈希缓存和 AI/Python 分析流程，不将这些基础机制算作新增贡献。

## 1. 项目在做什么

我们基于 Argo 做加密策略研究扩展：检查并修正具体回测计算问题，增加市场状态、仓位、损益与费用分析，并支持独立复算和交付版本核验。

Argo 提供基础引擎、策略接口与图形应用。我们的分析扩展目前主要是 Python 脚本、命令行工具和结果表，尚未集成成 Argo 原生页面。MA60、EMA20、Williams14 是三个固定验收案例，不代表覆盖整个平台；策略经过历史探索后选定，当前结果不是独立样本外验证。

| 状态 | 含义 |
|---|---|
| 官方已有 | 在指定官方版本的源码或文档中确认存在，不表示逐个实际操作过 |
| 本地已修 | 本地修改版已有代码和专项测试，不表示上游已合并 |
| 已有原型 | 仓库有脚本和输出，适配当前案例，不表示已集成界面或支持任意策略 |
| 待完成 | 需要开发或复核，不能写成已交付 |
| 待核对凭据 | 有完成声明，尚需核对实际文件与链上记录是否对应 |

官方盘点版本：核心 `5000407e138e3d38bfa98f3318e02dd4fdbcaa17`；macOS 应用 `5a69473c26627b526dcf53c14c753e10cb7f2a77`。不把官方版本与我们本地修复版混为一谈。

## 3. Argo 需要修改什么、我们改到了哪里

前五项为所核查版本的具体计算或账户问题；第六项为适配收盘信号的成交模型扩展，不将它们笼统叫成六个 bug。

| 项目 | 原行为与问题 | 我们已做的修改 | 验收与边界 |
|---|---|---|---|
| EMA 历史窗口 | 只请求 period 根，用其均值初始化后没有剩余价格递推，退化为 SMA | 优先请求 3×period 根，不足时回退 period 根 | 长历史下不再始终等于 SMA；早期回退仍需说明 |
| 现金同步 | 账本现金改变，但用于查询和校验的余额未在该成交路径同步 | 成交后同步现金与 BuyingPower | 账户与账本一致；连续买单使用更新现金 |
| 含费买入校验 | 本金够，但加手续费后可能透支 | 将费用计入买入校验，并在实际成交时检查 | 含费不足、跳空后买不起应拒单；针对无杠杆现金账户 |
| Equity 与多币种估值 | 不同币使用当前币价格，现金与资产价值组合不一致 | 用各币最新价格估值，按账户定义核对 | 验收现金加各币多头持仓市值，不由此宣称验证了融资或衍生品 |
| 数量精度 | 浮点残差使应卖 0.09 截成 0.08 | 调整边界并增加残差、高精度回归 | 同时检查少卖与超卖；有限测试不保证所有数量级正确 |
| 下一根开盘成交 | 收盘信号却按当根高低价中点成交，不符合本项目时间假设 | 增加可选 next-bar open 市价单执行 | 当根不成交、下一根按 Open、成交时重查现金；仅延迟市价单 |

**当前是本地已修，不是官方已合并。** 对外提交每条问题，应附原版本、触发条件、预期/实际行为、修改和测试。限价单子用例隔离属于测试修复，不是新增限价单功能。

EMA20 的当前本地方案：不足 60 根时回退最近 20 根 SMA；满 60 根后，用滚动 60 根中的前 20 根初始化，后 40 根递推。它不是完整历史连续递推。当前较长取数失败也会回退，并未只区分历史不足。后续需明确预热能否交易、窗口、初始化和错误处理；修改约定后要重新回测。

专项测试覆盖成交延迟、Open 定价、跳空/费用不足、连续买单现金、余额对账、双币种 Equity 与精度边界。完整 Go 测试此前有全绿日志；本次 WSL 返回访问拒绝，未重新执行。历史日志不等于当前任意构建均已通过。

## 4. 我们添加的核心功能：回测结果诊断

这是量化业务部分的主要交付。当前适配三案例，尚不是任意 Argo 项目都能直接导入的通用产品。

| 功能 | 使用者能回答什么 | 实际输出 | 代码与状态 |
|---|---|---|---|
| 统一共享账户净值 | BTC/ETH 共用现金后，每天账户值多少？ | 按成交重建现金与持仓，逐笔现金核对，每日净值与回撤 | `final_project/build_cases.py`；已有原型 |
| 同口径基准比较 | 比简单持有多赚多少、风险差多少？ | 自建 BTC/ETH 初始各半买入持有基准，买入扣费；收益差与相对财富增长 | `final_project/regime_analysis.py`；已有原型 |
| 市场状态分析 | 近期上涨、下跌或震荡之后，策略分别怎样？ | 用 t-1 已知的 BTC 过去 30 日收益分类；不足窗口不分类 | 同上；已有原型 |
| 仓位分析 | 差异来自持仓表现，还是主要因为空仓？ | 有仓天数、开盘成交后敞口、平均敞口、收盘敞口 | 同上；已有原型 |
| 每日损益与费用拆分 | 损益来自价格变化还是手续费？ | 隔夜价格损益、日内价格损益、费用；与净值变化核对，不一致报错 | 同上；已有原型 |
| 跨案例汇总 | 三个策略能否按同一口径比较？ | 全期收益/回撤、基准差、分状态、仓位和费用表 | `final_project/cases/summarize_cases.py`；已有原型 |

“新增”指我们在本项目实现的扩展，不是行业首创。Argo 已有基准与统计；我们的具体增量是统一共享账户、状态、敞口、损益拆分与核对这一套分析。

### 一个可直接演示的发现

相同“近期下跌”状态中，MA60 有仓 11/329 天，EMA20 为 27/329 天，Williams14 为 303/329 天。用户可以看出策略暴露方式不同，再结合收益与费用解释，避免只按累计收益排序。

### 分析边界

- 基准是自建持有组合，不是正式指数；初始各半不表示每日再平衡。
- 收益率相减不是年化超额，也不是风险调整后的 alpha。
- “下跌”表示过去 30 日已经下跌后的一组交易日，不是完整熊市；日期可不连续。
- 每日损益拆分是会计拆分，不是完整因子归因。
- 单位敞口值在低仓位时不稳定，只作辅助，不用来证明信号有效。
- 已发生费用拆分不等于改变费率后重跑。成本变化可能改变数量与成交。
- 当前结果不代替样本外、滚动验证或多重检验控制。

## 5. 我们添加的辅助检查与交付核验

| 功能 | 已经可以做什么 | 当前限制 |
|---|---|---|
| 日期联查 CLI | 查看某日价格、指标、预热、信号/无动作理由，关联次日成交与账户 | 三固定案例；不是原生页面，也不是任意策略自动解释器 |
| 独立 Python 重放 | 先从行情与配置计算交易，再读取原账本比较 | 三固定规则的一致性检查，不证明策略有效或平台全部正确 |
| 基础实验记录与比较 | 输出配置、数据指纹、结果、run_id，并比较记录 | 代码提交号写死；相同输入同路径可能覆盖；没有完整父实验、搜索与失败记录，不是完整实验管理系统 |
| 审计包 | 关联数据、配置、代码信息、成交、每日净值与文件指纹 | 来源版本需核对；哈希一致不代表计算或数据真实 |
| 本地文件核验 | 演示原文件指纹匹配、修改后不匹配 | 检查版本，不替代独立复算 |
| 链上登记与读链 | Xinyue 已接入 Hardhat，三份 v2 包在 chainlab 登记为记录 9、10、11；分别保存真实凭据 | 依据已保存的独立只读复查，三案例均原包通过、修改副本失败、原包再次通过；不替代 Argo 工程测试。见 [结果与证据](chainlab-results.md) |

本次重新运行三案例独立重放，共 730 笔：日期、币种、方向、数量、价格和费用一致，现金与日净值差约 1e-11 USDT。它是计算一致性证据，不是 730 次盈利验证。

链上验收证据已由 Xinyue 提供并核对：包路径与 SHA-256、网络/chain ID、合约地址、交易哈希、recordId 及读链结果均见 [测试网结果](chainlab-results.md) 和 `evidence/2026-11-20-chainlab-final-verification.json`。三个案例共 9 次核验符合预期，PR #1 已合入。审核者无需私钥；Qiyuan 跨电脑复查结果待确认。来源文件曾在上链前逐项核对，但 `chainlab:verify` 尚未自动逐项检查外部源码与配置。

链上的定位是跨团队交付时的版本登记，不证明回测正确，也不会把模拟成交变成真实链上交易。内部研究是否需要它，由场景决定。

## 6. 怎么运行、看什么结果

在仓库根目录、已安装依赖的 Python 环境中执行：

```powershell
python final_project/build_cases.py
python final_project/cases/summarize_cases.py
python final_project/independent_replay.py
python final_project/inspect_case.py --case ma60 --day 2022-03-02
python audit/verify_local.py
```

这些命令检查保存案例，不会重新构建运行 Go 引擎。最后一条针对原 MA60 v1 包，不等于自动核验三份 v2 包或读链。

主要输出：

- [三案例结果表](../final_project/cases/three_cases.md)：基准、市场状态、仓位、费用。
- `final_project/cases/<case>/`：各案例审计包和分析输出。
- [独立验证结果](../final_project/cases/independent_validation.json)：逐笔与每日净值差异。

`run_record.py` 可记录和比较，但正式留档前应修正写死版本及覆盖限制。

## 8. 汇报怎样概括

> 我们基于 Argo 修正特定回测路径的计算问题，并实现结果诊断原型：统一账户与基准，按市场状态比较策略，结合仓位拆分价格损益和手续费。三个固定案例经过独立重放，交付包可进一步做链上版本登记与核验。
